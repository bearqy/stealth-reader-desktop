# 开发规范

## 1. 当前阶段

当前仅维护产品与技术文档。除非里程碑正式进入开发状态，不添加应用脚手架、业务代码、构建流水线或发布密钥。

## 2. 分支策略

- `main`：始终保持可审阅状态。
- 功能分支：`codex/<topic>` 或 `feature/<topic>`。
- 修复分支：`fix/<topic>`。
- 文档分支：`docs/<topic>`。

所有重要变更通过 Pull Request 合并，避免直接向 `main` 推送未审阅的大范围改动。

## 3. 提交规范

建议采用 Conventional Commits：

```text
docs: define local-first MVP scope
feat: add global shortcut manager
fix: restore hidden window after display change
chore: update electron dependency
```

每次提交只解决一个清晰问题，不混入无关格式化或重构。

## 4. Pull Request 要求

PR 描述至少包含：

- 变更目的。
- 用户可见影响。
- 安全与隐私影响。
- 跨平台影响。
- 验证方式。
- 截图或录屏（涉及界面时）。
- 回滚方式（涉及数据迁移或自动更新时）。

## 5. 代码质量

进入开发阶段后启用：

- TypeScript strict mode。
- ESLint 与 Prettier。
- 单元测试与组件测试。
- Electron 主进程、preload 和 renderer 的独立边界检查。
- 禁止在代码中提交密钥、证书和个人路径。
- 依赖版本锁定及自动化更新审查。

## 6. 测试分层

### 6.1 单元测试

- 状态机、快捷键映射和配置迁移。
- TXT 编码识别与章节解析。
- URL、协议、下载路径和 IPC 参数校验。

### 6.2 集成测试

- 主进程与 preload IPC。
- 标签创建、崩溃和恢复。
- SQLite 迁移与数据清除。
- 文档解析 worker。

### 6.3 端到端测试

- 新用户首次启动。
- 打开网页、切换标签、收藏和恢复会话。
- 导入文档、搜索、改变样式和恢复进度。
- 透明、置顶、隐藏、老板键和托盘组合。

### 6.4 实机测试

系统级窗口行为不能只依赖自动化测试。每个发布候选版本需要在 macOS 和 Windows 实机验证。

## 7. 数据迁移

- 每个 schema 变更必须有递增版本。
- 迁移前创建必要备份。
- 迁移失败不得覆盖原数据。
- 不允许通过“删除全部用户数据”解决常规升级问题。

## 8. 发布规范

- 正式包必须由 CI 的受保护环境构建。
- 签名证书和公证凭证不得进入仓库。
- 发布前生成变更日志和校验信息。
- 先发布内部测试渠道，再逐步扩大。
- 自动更新必须支持暂停和回滚。

## 9. 文档维护

- 产品范围变化同步更新 PRD 和路线图。
- 安全边界变化同步更新安全文档。
- 重要、长期有效的技术选择使用 ADR 记录。
- 已被替代的 ADR 不删除，标记为 Superseded。
